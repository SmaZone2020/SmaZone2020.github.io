# IWantKnowSth：自托管个人信息终端

> 把散落各处的信息源——RSS 订阅、新闻接口、四家学术论文库——聚合到一个地方，按时自动抓取入库，再用 AI 帮你筛选、理解、回溯。数据全在本地，不依赖任何第三方平台即可运行。

## 为什么做

我订阅的信息源散在好几处：RSS 阅读器、博客、arXiv、各家的 News API。每天要打开好几个地方才能知道"今天发生了什么"，看完又得手动整理哪些值得精读。于是想做一个自己的终端：一处订阅、一处抓取、一处阅读，再加一层 AI 帮我判断"这篇值不值得读"。

产品名叫 IWantKnowSth——"我想知道点什么"。定位不是传统 RSS 阅读器，而是个人情报工作台。

## 能做什么

### 信息聚合

两类来源，统一入库到一张文章表：

- **RSS / Atom 订阅**——导入任意 Feed 地址，服务端抓取解析。
- **HTTP 新闻源**——配置任意接口，支持 GET / POST 等方法、请求头、请求体；响应按灵活规则解析：JSON（JSONPath 字段映射）、HTML（CSS 选择器）、XML（RSS/Atom 自动识别）。表单内置测试，先试后存。
- **定时抓取**——每个来源可配每日多个时段（如 `08:30, 20:00`），服务常驻时自动执行。

### 论文检索

统一接入 OpenAlex、arXiv、Semantic Scholar、Crossref 四家服务。按年份区间、最低被引、学科领域筛选，按相关度/被引/年份排序；输入时基于 OpenAlex 提供标题联想。结果一键收藏到"稍后读"。

### AI 解读

对单篇文章生成一句话概括、核心要点与背景关联，SSE 流式输出。系统提示词随界面语言（简中/英文）切换。

### 信使

面向本地资料库的对话式 AI 助手。它通过**工具调用**访问数据——回答永远基于工具返回的真实内容，不凭空编造。16 个工具覆盖查询文章/论文、管理信息源、收藏/标记已读。会话记录持久化，进页面自动恢复，可一键清空。

### 阅读管理

已读/未读、收藏/稍后读、分类归档，FTS5 全文搜索，阅读足迹，信息流可"按文章/按源/按日期"排版。移动端全响应式，固定底部导航。

### 系统能力

简中/英文双语言（默认跟随浏览器）、深色模式（跟随系统/手动）、10 个 AI 供应商预设、98 个精选 RSS 预设、一键部署。

## 快速开始

```bash
npm run start:prod
```

安装依赖 → 构建 → 启动，默认监听 `localhost:3000`。首次启动创建账户即可使用。数据库迁移在启动时自动执行，克隆后开箱即用。

## 技术实现

### AI 层：与协议无关的抽象

这个项目最核心的工程是 AI 层。它刻意**不绑定任何 SDK**，只用一层薄抽象把三种协议统一起来：

```
src/lib/ai/types.ts        AiChatMessage / ToolCall / ChatStreamEvent(text | tool_calls)
src/lib/ai/openaiChat.ts / openaiResponse.ts / anthropic.ts
                            统一签名 chatStream(messages, config, tools?, signal?)
                            各自手写 fetch + SSE 行解析，流内组装文本增量与工具调用
src/lib/assistant/agent.ts  runAgent：模型提议工具 → 服务端执行 → 结果回填 → 再调（≤8 轮）
```

三个 provider 的 `chatStream` 返回判别联合 `{type:'text'}` 或 `{type:'tool_calls'}`，单一代码路径承载"流式文本"和"工具调用"两种语义。文章解读路由复用同一条管线，只需过滤 text 事件。

协议差异各自适配：

| 协议               | 工具调用组装方式                                 |
| ---------------- | ---------------------------------------- |
| OpenAI Chat      | 按 `index` 逐分片拼装流式 tool_calls             |
| OpenAI Responses | 按事件模型（`function_call_arguments.delta`）组装 |
| Anthropic        | content block 数组，且需处理"角色必须交替"约束          |

### 数据即工具

为了控制上下文体积，数据获取本身就是工具：`get_news_list` 只返回 id/标题/摘要/来源，需要详情再调 `get_news_content`。模型拿到的永远是裁剪后的数据，上下文不会随工具结果膨胀。工具全部在服务端执行（直接调 DB 与领域函数），客户端只收到 `start / delta / tool / done / error` 五类 SSE 事件。

### 会话持久化

会话记录存 `assistantMessages` 表（单会话，追加式）。每次请求重新跑 agent——数据是确定性的本地库，重查结果一致，因此不把工具结果塞进持久化上下文。失败中断后残留的悬空 user 消息会在下次请求时自动清理，保证消息角色交替。

### i18n 与主题

- **自研轻量 i18n**（没引 next-intl）：14 个领域 × 2 语言的手写词典，`en satisfies typeof zhCN` 在编译期保证两语言键完全对齐——缺键、多键直接编译报错。`t(key, params)` 走点路径查找 + 插值。
- **深色模式**：全部颜色走 `@theme` 的 `--color-*` 令牌，`html.dark` 整体覆盖令牌即完成明暗翻转，组件零 `dark:` 变体，无白闪。

### 数据层与调度

SQLite 单文件 + WAL，better-sqlite3 同步调用（单用户场景无连接池复杂度）；Drizzle ORM 定义 schema，迁移文件入库，新机器克隆后启动自动建库。FTS5 外部内容表做全文索引，bm25 排序。定时任务由 `instrumentation.ts` 启动的调度器每分钟扫描各源 `scheduleSlots` 触发抓取。

## 踩过的坑

最有代表性的是 **Anthropic 的 400**：信使问"最新的文章是什么"，AI 连续调了 3 个工具，agent 循环把 3 个工具结果各推成一条 `role:'tool'` 消息。OpenAI 接受连续 tool 消息，但 **Anthropic 要求消息角色严格交替**——3 条连续 user（tool_result）被直接 400 拒绝。修法：Anthropic 侧把连续工具结果合并进同一条 user 消息（多个 `tool_result` block）。这也说明"协议无关抽象"的另一面：协议差异得自己维护。

另一个取舍是**无状态 agent**：每次请求重新跑 agent，会重复调用工具取数。换来的是上下文始终小、回答可溯源、失败可自愈。

## 设计取舍

| 决策                     | 取舍                                    |
| ---------------------- | ------------------------------------- |
| 自研 AI provider 层而非 SDK | 三协议统一抽象、可指向任意兼容网关，但 SSE 事件解析的维护落在自己身上 |
| 手写轻量 i18n              | 零依赖、类型安全，但新增语言需人工维护词典                 |
| 工具取数而非上下文注入            | 上下文小、可溯源，但模型需学会工具调用，多轮会重复取数           |
| SQLite 同步直查            | 单用户简单可靠，无并发写扩展性（自托管场景可接受）             |
